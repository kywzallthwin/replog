# W2-18: All-Exercises Chart Feed

State: done

## Goal
Show every logged exercise's progress chart on one `/progress` page and let the user drill into one exercise's full session history without a network round trip.

## Dependencies
- W2-08 establishes the kg/lb display-unit contract reused by the feed metrics.
- W2-09 provides the dependency-free SVG chart reused inside each feed card.

## Scope
- `GET /api/progress` returns an additive `exerciseSummaries` array (personal best, stats, session history, chronological trend) for every logged exercise, computed from the existing single set-log query with no extra database round trips.
- `client/src/lib/progress.ts` exposes the `ProgressExerciseSummary` type and normalizes payloads that omit `exerciseSummaries` by falling back to the selected exercise.
- `/progress` renders a responsive all-exercises feed (`grid gap-4 lg:grid-cols-2`) with one card per exercise: name, category badge, `View history` action, PB/progress/sessions/heaviest metrics, and an inline SVG chart.
- The exercise selector gains an `All exercises` option when more than one exercise is logged; switching between feed and exercise resolves from the cached payload.
- A single-exercise detail view (PB card, stat tiles, chart, session history cards/table) is reachable from the feed, the selector, and `/progress?exerciseId=...`, with an `All exercises` back action.

## Out of scope
- New metrics, date-range filters, chart zooming, or a charting dependency.
- Changing the existing top-level `/api/progress` response fields or their meaning.
- Database schema changes.

## Acceptance criteria
- `exerciseSummaries` covers every logged exercise and matches the existing top-level payload for the selected exercise.
- The feed shows one chart, PB, and unit-aware stats per exercise at once.
- Selecting an exercise or tapping `View history` opens its full session history; `All exercises` returns to the feed without a refetch.
- Existing single-exercise, empty-state, error-state, and kg/lb behaviour keeps working.

## Verification
- Focused client progress-page tests and the server progress/session test.
- `npm run check`.

## Stop conditions
- Do not add server round trips per exercise, new chart dependencies, or schema migrations.
- Do not change the existing `/api/progress` top-level contract.
