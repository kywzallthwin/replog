  - Independent code/database/security review completed and full `npm run check` passed.

## Goal
Allow owners to rename, recategorize, and remove their custom exercises without corrupting historical workouts.

## Scope
- Add owner-only update and delete contracts for custom exercises; global catalog exercises remain immutable.
- Preserve normalized-name uniqueness across the global catalog and the owner's active custom exercises.
- Implement deletion as archival: hide the exercise from future catalog, add, and swap results while retaining its row for historical session references.
- Remove archived exercises from the owner's program days in the same transaction so new sessions do not include them.
- Preserve existing `SessionExercise.nameSnapshot` values and completed workout rendering.
- Add management actions and accessible confirmation/error states to the exercise picker or a focused custom-exercise management view.

## Out of scope
- Editing the global catalog, merging exercises, restoring archived exercises, or rewriting historical snapshots.
- Account-deletion cleanup, which remains in Wave 4.

## Acceptance criteria
- Owners can edit only their own active custom exercises.
- Duplicate normalized names are rejected consistently on create and update.
- Deleting a custom exercise removes it from future selection and program days but leaves past workouts readable.
- Another user cannot view, edit, or delete the custom exercise.
- Management and confirmation flows fit at 375px and restore focus correctly.

## Verification
- Focused exercise, program, session, and picker tests.
- Migration validation and `npm run check`.
- Manual 375px create/edit/delete flow with program and completed-history references.

## Risks And Rollback
- Risk: hard deletion would break foreign-key references or historical progress. Use an additive archival field and transactional program cleanup.
- Rollback: the additive column can remain unused if the UI/API change is reverted; do not drop historical exercise rows.
- Independent review is required for the migration and deletion semantics before `done`.

## Stop conditions
- Do not hard-delete exercises referenced by sessions or expand into account lifecycle cleanup.
